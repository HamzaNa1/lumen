# Media transcoding

## Decision

Use the installed FFmpeg decoder set and produce fragmented MP4 with H.264 and AAC (or WebM with VP8/Opus when that is the supported output) for incompatible browser media. Browser capability probes select direct delivery first; codec failures can retry with conversion. Preserve compatible H.264/AAC streams when repackaging a container at the beginning. Native desktop playback tries MPV's local decoders first. A missing video/audio decoder or a decoding failure triggers one server conversion to H.264/AAC, retaining the playback session and source position. Network errors do not trigger conversion. A server capability flag prevents fallback requests to older servers. Converted desktop playback uses the same administrator policy, resource limits and authenticated media endpoint as browser playback; stream replacement on seeking or audio selection retains pause state and cancels the preceding request. Unavailable conversion is surfaced as a playback error rather than retried indefinitely.

Stream through bounded pipes rather than creating a full-file cache. Cancellation terminates FFmpeg, closes its output pipe, and escalates to a forced kill; the scheduler releases capacity after the process closes. Session authorization is rechecked during streaming. An inactive consumer has a bounded lease. Reject excess work instead of building an unbounded queue.

For converted playback, a seek replaces the stream. Encode video and audio after a nonzero seek: copying packets from the preceding keyframe introduces an unknown timeline offset and can break audio synchronization. This sacrifices the video-copy optimization during seeking in exchange for predictable positions. Ordinary direct playback retains file range seeking. Desktop resumes converted playback with a fresh stream because a paused consumer can outlast the server's bounded idle lease; keeping that lease unbounded would retain encoder resources indefinitely.

Offer CPU encoding, NVIDIA NVENC and Linux VAAPI with explicit device lists and least-loaded allocation. CPU decoder/filter/encoder thread limits and global/per-device admission limits bound concurrency. Hardware selection is explicit: driver or encoder failures do not silently consume CPU capacity beyond the administrator's policy. VP8 output uses software encoding, subject to an explicit software-video permission and the same global/thread limits. Hardware decoding and automatic GPU discovery are separate future decisions. The server image uses distribution FFmpeg and VAAPI drivers so encoders can load host GPU drivers; fully static FFmpeg was rejected because it cannot provide the offered NVENC/VAAPI paths. Image smoke checks require the advertised encoders.

This establishes broad input codec support through FFmpeg, not a promise of every Jellyfin feature. Output is currently H.264/AAC or VP8/Opus, converted audio is stereo, and there is no subtitle burn-in, HDR tone mapping or Dolby Vision preservation.

### Adaptive quality

Servers that advertise `adaptiveStreaming` also convert video into 4-second MPEG-TS pieces in a ladder of capped qualities (1080p at 8 Mbit/s down to 360p; never above the source), served as HLS under `/api/v1/media/<track>/adaptive/<audioIndex>/` with the session's grant. Every quality and every encoder restart cuts at the same source times: FFmpeg keeps source timestamps, forces a keyframe on the first frame at or after each multiple of four seconds, and cuts only at keyframes. Video pieces carry no audio; one audio stream is shared by all qualities, so a quality change never touches the sound. Each session runs one encoder, at the quality and position clients ask for, which takes the session's transcoding slot and stops once it is two minutes ahead of any request. Pieces live under `<dataDir>/transcode` until the session ends or goes idle, and that directory is emptied at startup.

Clients choose quality with the shared rules in [`AdaptiveQuality.ts`](../../packages/client/src/playback/adaptive/AdaptiveQuality.ts), from the connection measured by piece downloads. A step down keeps every piece already held; a step up refetches held pieces past a margin that covers fetching a better one, so it shows within seconds without waiting for the buffer to play out. The browser plays the pieces through hls.js with its own quality choice turned off. The desktop bridge serves MPV a single-quality HLS stream and decides each piece itself, replacing a held piece only once the better one has arrived. Moving between the original file and converted pieces replaces the stream, so Auto does it only on strong evidence; returning to the original is a separate, removable rule in [`OriginalQuality.ts`](../../packages/client/src/playback/adaptive/OriginalQuality.ts). Older clients and browsers without MediaSource keep the single-stream conversion above. Actual input support depends on the installed FFmpeg build; GPU execution additionally depends on drivers and device access. CPU and real-browser tests cannot certify GPU hardware.

Persist transcoding policy in the server database and expose it only to administrators through Settings. Each new conversion reads the current policy, so saving requires no restart. Existing jobs retain their settings until completion; disabling conversion cancels active jobs and pending starts. Environment overrides were rejected to keep one authoritative configuration surface.

## Alternatives

- Full-file conversion caches need storage quotas, eviction and partial-file ownership while continuing work viewers no longer need.
- Restarting a single capped stream at a new quality was simpler, but every change would rebuffer and drop what was already fetched. Seamless changes need pieces cut at the same times in every quality.
- Encoding every quality continuously would make each switch instant, at a multiple of the CPU a home server has.
- Fragmented MP4 pieces carry each quality's parameters in a separate initialization segment, which MPV cannot switch between inside one stream; MPEG-TS repeats them in every piece.
- Unrestricted CPU fallback after hardware failure makes resource use unpredictable under load.
